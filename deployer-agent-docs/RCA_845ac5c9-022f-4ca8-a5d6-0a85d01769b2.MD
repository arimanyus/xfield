# RCA — "Sign in with X" failing on LIVE deployment

**App:** handle-prophecy  |  **Live URL:** https://handle-prophecy.emergent.host  |  **Active run:** 845ac5c9-022f-4ca8-a5d6-0a85d01769b2 (redeploy, success)
**Frontend:** Cloudflare  |  **Mode:** debug-only (no deploy / no secret changes made)

## Problem statement
Users report "sign in with X" fails on the live domain. Preview already ruled out (preview login + a real X sign-in succeeded on 2026-10-25). Asked to inspect the live deployment only.

## What I verified (evidence)
1. **Live deployment is up and serving the current build.**
   - `GET /api/auth/me` → `200 {"enabled":true,"user":null}`.
   - Backend logs show only clean `Application startup complete.` lines — no startup errors / tracebacks.
   - No custom domains attached (`list_domains` empty) — live host is the default `handle-prophecy.emergent.host`.

2. **Login redirect is CORRECT in production.** Probed live without following redirects:
   - `GET /api/auth/x/login` → `302` → `https://x.com/i/oauth2/authorize?response_type=code&client_id=T1VVaDRLU1VCcnQ1SmlhSmJOM186MTpjaQ&redirect_uri=https%3A%2F%2Fhandle-prophecy.emergent.host%2Fapi%2Fauth%2Fx%2Fcallback&scope=tweet.read+users.read&state=...&code_challenge=...&code_challenge_method=S256`
   - **redirect_uri = `https://handle-prophecy.emergent.host/api/auth/x/callback`** — correct for the live host.

3. **Production secrets** (names only; values never read):
   - `X_CLIENT_ID` — present, not empty.
   - `X_CLIENT_SECRET` — present, not empty.
   - `WEBHOOK_CRON_SECRET`, `ADMIN_KEY`, `MOVEINS_PER_HOUR`, `TOWN_CAPACITY` — all present.
   - **`PUBLIC_BASE_URL` — NOT set.** This is NOT the defect: `public_base()` in `backend/server.py` falls back to the `x-forwarded-host` header, which resolves to `handle-prophecy.emergent.host` (confirmed by the correct redirect_uri above).
   - `TWITTERAPI_IO_KEY` — empty, but unrelated to the OAuth login flow.

4. **The callback never reaches the backend.** Over the last 24h the backend logged:
   - 5× `GET /api/auth/x/login ... 302 Found`
   - **0× `/api/auth/x/callback`**, and **no** `X token exchange failed` / `X users/me failed` lines.
   If the callback were reaching the backend and failing (state mismatch, token-exchange 4xx, users/me error), it would appear in logs and redirect with `/?signin=expired|cancelled|x_error`. None of that exists — the browser is never bounced back to our callback at all.

## Root cause (proven mechanism + the one unobservable variable)
Login works and sends X a correct, well-formed PKCE request with `redirect_uri = https://handle-prophecy.emergent.host/api/auth/x/callback`. X then never redirects the user back — the callback endpoint receives zero hits. The only remaining variable, given a healthy backend, correct redirect_uri, and present client credentials, is the **X app's OAuth 2.0 "Callback URI / Redirect URL" allowlist in the X Developer Portal**: it contains the preview callback (`https://handle-prophecy.preview.emergentagent.com/api/auth/x/callback`, which is why preview succeeded) but **does not contain the production callback `https://handle-prophecy.emergent.host/api/auth/x/callback`**. On a redirect_uri the app doesn't recognize, X blocks the authorization and never returns to our server — exactly matching "login 302 works, callback never fires."

This is an **inference**, not reproduced end-to-end: I cannot drive a real X authorization or see the X Developer Portal from here. Everything on our side (reachability, build, redirect_uri, client credentials, logs) is confirmed healthy via the tool results above, which is why the remaining cause sits on the X app registration.

## Suggested fix
**User — X Developer Portal (third-party):** In the X app's User authentication settings, add the production callback URL to the allowed Callback URI / Redirect URLs:
`https://handle-prophecy.emergent.host/api/auth/x/callback`
Keep the preview URL too if preview is still used. Confirm the app's Client ID in the portal matches the live `X_CLIENT_ID` (`T1VVaDRLU1VCcnQ1SmlhSmJOM186MTpjaQ`). Then retry sign-in on the live domain.

**(Optional hardening, not the cause):** Setting `PUBLIC_BASE_URL=https://handle-prophecy.emergent.host` in the Secrets tab would pin the redirect_uri instead of relying on `x-forwarded-host`. Current behavior is already correct, so this is precautionary only.

## How to confirm the fix
After adding the callback URL in the X portal, retry sign-in on the live site. On success the backend will log a `GET /api/auth/x/callback ... 302` and a session cookie will be set; `/api/auth/me` will then return a populated `user`.
